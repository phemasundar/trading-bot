# Trading Bot - Global Context & Constraints

## Core Objective

- **Architecture**: A modular, event-driven Options Trading Bot built on Java and Spring Boot. It executes automated strategies based on dynamic technical indicators and options market data. Frontend logic is modularized into domain-focused JS modules under `static/js/` aggregated via `app.js`. Strategy definitions reside in `strategies-config.yml`, while static Greek polarities by strategy type are centralized in `strategy-greeks.yml`.
- **Runtime Goals**: Maintain low-latency execution, resilient error handling, and reliable asynchronous processing. Core integrations include the Charles Schwab API for market data/trading, and Supabase for persistent tracking of IV data (used for IV Rank and IV Percentile filters with >=20 historical records required; detailed in `docs/implied-volatility.md`), execution history, historical trade deduplication (`historical_trades`), and filter configuration.
- **Design Philosophy**: High reliability with strict fail-safes. Technical and fundamental filters, indicator thresholds, and strategy constraints must remain externalized in configuration (e.g. YAML), utilizing dynamic mathematical expression evaluation rather than hardcoded logic. Strategy static Greeks are decoupled into `strategy-greeks.yml` to prevent configuration bloat.
- **Timezone Convention**: All timestamps across the app use **`America/Chicago` (CDT/CST)** — Dallas, TX local time. Enforced via `spring.jackson.time-zone=America/Chicago` in `application.properties` and `-Duser.timezone=America/Chicago` JVM arg in `ci.yml`. Market data zone (`America/New_York`) is used only for NYSE trading-day boundary logic in `TradeHashUtil` and `TechnicalIndicatorUtils`.
- **UI Design System**: Dark and light theme tokens are centralized in `style.css`. Form input placeholders use `--text-placeholder` (`#94a3b8` in light mode, `#64748b` in dark mode) to ensure filter hint values remain visually distinct from filled inputs across all dashboards and strategy execution pages.
- **Earnings Filtering**: Legacy boolean `ignoreEarnings` is deprecated in favor of `earningsFilters` with mathematical expression conditions (`DAYS_TO_NEXT_EARNINGS`, `EARNINGS_NEAREST_TO_DTE`, `DTE`). The Execute Strategy interface provides preset options and custom condition entry mapped directly to `earningsFilters.conditions`. Internal evaluation expressions (`earningsFilterExpressions`) are marked `@JsonIgnore` and ignored via `SKIP_KEYS` to eliminate duplicate rendering, preserving exclusively the formatted `📅 Earnings Filters` section.
- **LEAP Cost Filtering**: Redundant Cost Efficiency Filter is removed. Cost Savings Filter (`minCostSavingsPercent`), Margin Interest Rate, and Savings Interest Rate carry no hardcoded defaults in code; user input and YAML config take priority, and when unconfigured, all candidate trades pass the cost filter.
- **Custom Execution In-Place Re-execution**: Custom execution cards on `/execute.html` offer compact **"⬆ Load"** and single-click **"▶ Execute"** buttons alongside **"🗑 Delete"**. Clicking **"▶ Execute"** loads parameters into the form and re-executes the strategy while updating the existing record in `custom_execution_results` via PATCH and replacing results in the existing card without duplicate card generation.
- **Universal Indicator Registry & Persistence**: `securities-filters.yml` serves as the master indicator catalog and whitelist registry (specifying allowed periods for RSI, Bollinger, SMAs, EMAs, Volume SMAs, Highs 5/20/252, ATR, and HV). `StrategiesConfigLoader` performs fail-fast startup validation on bootstrap against this whitelist, rejecting unconfigured periods at startup or runtime, while `TechnicalIndicatorPreCalculationService` deterministically pre-calculates and persists all cataloged indicators into Supabase table `latest_security_indicators` via `SecurityIndicatorsRepository`.
- **Securities Screen & Dynamic Indicator Tracker**: The `📁 Securities` research screen (`/securities.html`) dynamically discovers all securities list YAML files under `securities/`, rendering collapsible blocks with lazy-loaded data from Supabase (`POST /api/securities/data`). Each security displays a non-tabular 2-column card featuring a priority-tiered alert badge (RSI oversold/crossover > 50 SMA > lower BB > 20 SMA), narrative summary, price action progression bar, dynamic indicator tracker (MAs, EMAs, RSI, BB, Volume, Volatility), and rule-based trading playbook callout configured via `securities-filters.yml`.

## Coding Standards

- **Java Best Practices**: Write clean, modern Java (JDK 21+). Adhere to SOLID principles, favoring composition over inheritance and immutability where applicable.
- **Spring Boot Ecosystem**: Effectively leverage Spring's dependency injection, properties configuration, and application events. Keep business logic decoupled from framework-specific web layers.
- **Boilerplate Reduction**: Use Lombok extensively (`@Data`, `@Builder`, `@NoArgsConstructor`, `@AllArgsConstructor`, `@Slf4j`, `@UtilityClass`) in all new models, DTOs, and config classes to minimize boilerplate.
- **Null Safety**: Standardize null and emptiness checks using Apache Commons (`StringUtils.isBlank`, `CollectionUtils.isEmpty`). Ensure collections are returned as empty lists rather than nulls.
- **Testing Requirements**: Enforce a minimum of 85% instruction coverage for core business logic using TestNG and standard mocking frameworks.
- **Strategy Identity**: Strategy IDs are decoupled from securities files (`Alias [- TermType]`) to guarantee deterministic and stable trade hashes in `historical_trades`. Ticker universe configs (`securitiesFile`, `securities`) and technical filter configurations (`technicalFilters`) are persisted in `filterConfig` and formatted cleanly into human-readable representations in Filter Details (preventing `[object Object]` serialization).
